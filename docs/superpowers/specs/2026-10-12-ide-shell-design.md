# YAL IDE — 기본 틀(1단계) 설계

날짜: 2026-10-12
상태: 사용자 검토 대기

## 1. 목적

게임 개발을 위한 IDE. 여러 프로젝트를 한 곳에서 관리하고, 프로젝트를 선택하면 그 프로젝트에 연결된 Claude(Claude Code)를 바로 띄운다. 작업 방식은 "Claude가 지시·검수, GPT(Codex)가 결과물 생성"을 기본으로 한다.

VSCode와 비슷한 외형을 가지되, 파일 탐색기는 두지 않는다. 그 자리에 프로젝트 목록이 온다.

## 2. 범위

### 포함 (1단계)
- Electron 독립 데스크톱 앱
- 프로젝트 목록: 추가 / 삭제 / 선택
- 프로젝트별 Claude Code 터미널 (프로젝트마다 독립 세션, 앱 재시작 시 이어받기)
- 프로젝트 등록 시 `CLAUDE.md`, `scripts/gpt.sh` 자동 구성 (Claude 지시 → GPT 작업 구조)
- **프로젝트별 작업 상태 표시**: 여러 프로젝트를 동시에 돌리며 목록에서 한눈에 확인하고 오가며 컨펌한다 (§5 StatusTracker)

### 제외 (이후 단계)
- Skill 학습 시스템 (2단계, 아래 §9)
- GPT 작업 진행 패널
- 코드 뷰어·편집기 (Monaco)
- 게임 엔진별 전용 기능

## 3. 기술 선택

| 항목 | 선택 | 이유 |
|---|---|---|
| 앱 | Electron + React + TypeScript | 이후 Skill 제안 화면, GPT 패널을 얹기 쉽다 |
| 터미널 | xterm.js + node-pty | 실제 셸이므로 Claude Code가 그대로 동작 |
| Claude 연결 | 터미널에서 `claude` 실행 | 스킬, 권한, 메모리, CLAUDE.md 등 기존 기능을 그대로 사용 |
| 세션 이어받기 | `claude --continue` | Claude Code가 폴더별 세션을 저장하므로 별도 데몬 불필요 |
| 목록 저장 | 앱 데이터 폴더의 JSON | 단순하고 충분 |

## 4. 화면

- 왼쪽: 프로젝트 목록 (이름, 경로, 실행 중 표시, 추가 버튼)
- 오른쪽: 선택한 프로젝트의 Claude 터미널
- 파일 탐색기 없음

## 5. 구성 요소

각 요소는 하나의 역할만 가지며 인터페이스로만 소통한다.

### ProjectRegistry
- 역할: 프로젝트 목록의 저장·조회·추가·삭제
- 데이터: `{ id, name, path, addedAt }`
- 의존: 파일 시스템(앱 데이터 폴더)
- 규칙: 삭제는 목록에서만 제거한다. 프로젝트 폴더는 건드리지 않는다.

### TerminalManager
- 역할: 프로젝트별 pty 세션 생성·유지·종료, 입출력 중계
- 규칙: 프로젝트를 전환해도 이전 세션은 유지한다. 프로젝트 삭제 시 해당 세션만 종료한다.
- 시작 명령: 기존 세션이 있으면 `claude --continue`, 없으면 `claude`

### Provisioner
- 역할: 프로젝트 등록 시 `CLAUDE.md`와 `scripts/gpt.sh` 생성
- 규칙: **이미 있는 파일은 절대 덮어쓰지 않는다.** 생성한 파일 목록을 사용자에게 보여 준다.
- 템플릿: 현재 YAL_IDE 저장소의 `CLAUDE.md`, `scripts/gpt.sh`를 기준으로 한다.

### StatusTracker + HookSetup (작업 상태)
- 역할: 각 프로젝트의 Claude가 지금 무엇을 하고 있는지 알려 준다.
- 방식: IDE가 Claude Code를 `--settings <파일>`로 실행하며 훅(hooks)을 주입한다. 훅은 작은 스크립트로 `상태 폴더/<프로젝트id>.json`에 상태를 원자적으로 기록하고, 메인 프로세스가 이를 읽어 목록에 보여 준다. 화면 출력 해석이나 타이머 추측은 쓰지 않는다.
- 상태 4가지:

| 상태 | 표시 | 의미 | 전이 |
|---|---|---|---|
| `idle` | 평상시 | 대기 중 또는 세션 없음 | 초기값, 세션 종료·시작, 완료를 확인(프로젝트 선택)했을 때 |
| `working` | 작업 중 | Claude가 작업하는 중 | `UserPromptSubmit`, 입력 필요 상태에서 도구가 다시 실행될 때(`PostToolUse`) |
| `done` | 작업 끝 (컨펌 대기) | 한 턴이 끝나 사용자 확인을 기다림 | `Stop` |
| `attention` | 입력 필요 | 권한 요청 등 사용자 응답이 필요 | `Notification` (`idle_prompt` 알림은 무시) |

- 4번째 상태 `attention`을 둔 이유: 권한 확인을 기다리는 동안 `Stop`이 발생하지 않아 "작업 중"으로 잘못 보이기 때문이다.
- `done`은 사용자가 그 프로젝트를 선택하면 `idle`로 돌아간다 (확인한 것으로 간주).
- 상태 파일이 없거나 깨졌으면 `idle`로 취급한다.

### Renderer UI
- 역할: 목록과 터미널 화면 표시, 사용자 입력을 위 구성 요소에 전달
- 목록에는 프로젝트마다 상태 표시(색 점 + 짧은 문구)를 보여 준다.

## 6. 동작 흐름

1. **프로젝트 추가**: 폴더 선택 → ProjectRegistry에 등록 → Provisioner 실행
2. **프로젝트 선택**: TerminalManager가 해당 폴더에서 `claude` 실행 (기존 세션이 있으면 `--continue`)
3. **프로젝트 삭제**: 세션 종료 → 목록에서 제거 (폴더·파일 보존)
4. **앱 재시작**: 목록 복원. 프로젝트를 선택하면 `--continue`로 이전 대화 이어받기

## 7. 오류 처리

- `claude` 또는 `codex` CLI가 없거나 로그인되지 않은 경우: 터미널 대신 원인과 해결 방법을 담은 안내 화면 표시
- 등록된 폴더가 사라진 경우: 목록에 "경로 없음"으로 표시하고 세션을 시작하지 않음
- pty 비정상 종료: 상태를 "종료됨"으로 표시하고 다시 시작 버튼 제공
- 이미 등록된 경로 추가 시도: 중복으로 거부

## 8. 테스트

- 단위 테스트: ProjectRegistry (추가/삭제/중복/영속화, 삭제 시 폴더 보존), Provisioner (생성, 기존 파일 보존)
- 통합 확인: 실제 앱 실행 후 프로젝트 추가 → Claude 터미널 표시 → 전환 시 세션 유지 → 재시작 후 이어받기
- node-pty의 Windows 빌드 가능 여부는 구현 초기에 가장 먼저 확인한다 (§10 위험)

## 9. 이후 단계 메모 — Skill 학습 (2단계, 참고)

2단계에서 별도 설계한다. 지금까지 합의된 원칙만 기록한다.

- 학습 원천: (A) 사용자가 Claude에게 반복하는 지시·수정 요청, (B) GPT 결과물이 검수에서 반려된 이유
- 제외: (C) 프로젝트 코드 자체의 반복 구조 — 모델이 개선되면 낡은 구현 패턴에 묶이기 때문
- Skill에는 "무엇을 원하는지"(의도·기준)만 담고 "어떻게 짜는지"는 담지 않는다
- 자동 반영 금지: 변경안(diff)을 만들고 사용자가 승인해야 반영
- 증거 기준: 여러 세션에서 반복된 경우에만 제안
- 비용 통제: 규칙 기반 1차 필터 → 후보만 작은 모델로 요약, 세션 종료 시 또는 수동 실행
- Skill 길이 상한, 충돌·중복 정리, git 버전 관리와 롤백, 오래된 규칙 재확인(만료)

## 10. 위험과 미정 사항

- node-pty는 네이티브 모듈이라 Windows에서 빌드 도구나 Electron 버전 맞춤이 필요할 수 있다. 실패 시 대안은 구현 계획 단계에서 정한다.
- Claude Code의 `--continue` 동작과 세션 저장 방식은 CLI 버전에 따라 달라질 수 있으므로 구현 시 실제로 확인한다.
- 상태 훅은 `node`가 PATH에 있어야 동작한다. 없으면 상태 표시만 비활성화하고 터미널은 정상 동작하며, 안내를 보여 준다.
- 사용자가 Esc로 작업을 중단하면 `Stop` 훅이 발생하지 않을 수 있어 상태가 `working`으로 남을 수 있다. 실제 앱에서 확인하고, 필요하면 수동 초기화 수단을 추가한다.
- 훅 이벤트 이름과 알림 종류 필드(`notification_type`)는 Claude Code 버전에 따라 달라질 수 있어 구현 시 실제 페이로드를 기록해 확인한다.
- `scripts/gpt.sh`는 Codex의 `--approve-for-me` 옵션에 의존한다. 이 옵션의 보안 의미는 프로젝트 등록 시 사용자에게 한 번 안내한다.
