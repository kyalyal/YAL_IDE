# 에셋 공간 전환 및 기획-개발 병합 설계

작성일: 2026-10-13 · 상태: 사용자 설계 승인(채팅), 문서 검토 대기

## 1. 배경과 목표
- 기획은 게임마다 달라 재사용되지 않는다. 기획 프로젝트를 개발 프로젝트가 "참조(링크+변경 동기화)"하는 구조는 비용 대비 효용이 낮다.
- 재사용 가치가 있는 자산은 에셋(이미지·효과음·이펙트·UI 키트)이다.
- 목표: (1) 기획→설계→개발을 **개발 프로젝트 하나**에서 Claude(디렉터)→GPT(수행자) 구조로 진행한다. (2) 위쪽 '기획' 공간을 **GPT가 에셋을 만들어 쌓는 에셋 프로젝트**로 바꾼다. (3) 개발 프로젝트는 에셋을 **복사해서** 사용한다(게임 폴더만으로 빌드·출시 가능).

## 2. 공간 구조
| 공간 | kind 값 | 설명 |
| --- | --- | --- |
| 에셋 | `assets` (기존 `planning` 대체) | GPT가 에셋을 제작·검수·카탈로그화 |
| 개발 | `dev` | 기획·설계·구현·검증을 한 프로젝트에서 수행 |
| YAL_IDE 관리 | `manage` | 변경 없음 |

- 저장된 프로젝트 레지스트리의 `kind: 'planning'`은 로딩 시 `assets`로 변환한다(폴더·파일은 건드리지 않는다). 설정 파일은 변환 후 저장한다.
- 스킬 저장소: 기존 `spaces/planning/skills`의 내용은 §5대로 `spaces/dev/skills`로 병합하고, 원래 폴더는 삭제하지 않고 `spaces/planning-migrated`로 이름만 바꿔 보존한다. `spaces/assets/skills`는 새로 만들며 에셋 내장 스킬만 설치한다.
- UI 탭·목록 제목·i18n(ko/en)의 "기획"은 "에셋"으로 바꾼다. 개발 프로젝트 안의 기획 개념은 §4가 담당한다.

## 3. 에셋 프로젝트
- 규칙(스킬 `yal-asset-factory`, assets 공간 내장): Claude는 제작 지시서(용도, 스타일, 크기/포맷, 파일 경로, 수량, 완료 조건)만 쓰고 GPT가 제작한다. Claude는 에셋을 직접 만들지 않는다. 결과는 Claude가 읽고 검수하며 반려·재지시한다.
- 폴더 규칙: `images/`, `sfx/`, `vfx/`, `ui/`. 파일명은 `<분류>-<이름>-<버전>.<확장자>`.
- 카탈로그 `ASSETS.md`: 에셋마다 id, 용도, 스타일, 포맷, 크기, 경로, 태그, 제작일, 출처(자체 제작)를 한 항목으로 기록한다. GPT가 제작 후 갱신하고 Claude가 검수한다.
- 제작 가능 범위: SVG·캔버스 이미지, 웹오디오 합성 효과음 등 GPT가 실제 만들 수 있는 것을 구현 단계의 작은 테스트로 확인해 스킬에 "가능/불가·대안"으로 기록한다. 불가 항목은 "사용자 제공 필요"로 분리한다(BGM, 광고 연동, 스토어 출시 절차만 사람 몫이라는 기존 원칙 유지).

## 4. 개발 프로젝트가 에셋을 쓰는 방법
1. 개발 프로젝트에 에셋 프로젝트를 **하나 연결**한다. 기존 `linkedPlanningId`는 `linkedAssetsId`로 대체하며, 기존 링크값은 변환된 에셋 프로젝트를 그대로 가리킨다.
2. 연결된 에셋 프로젝트 폴더는 Claude 터미널에 `--add-dir`로 **읽기 전용 참조**로 노출한다(현재 기획 링크와 같은 방식).
3. Claude는 카탈로그 `ASSETS.md`를 읽고 쓸 에셋을 정한다. 복사는 GPT가 수행해 개발 프로젝트의 `assets/`에 넣고, 출처 id를 `assets/ASSETS-USED.md`에 기록한다.
4. 카탈로그에 없는 에셋은 **개발 프로젝트 안에서 GPT가 바로 제작**한다. 여러 게임에 쓸 만한 것을 에셋 프로젝트로 옮기는 자동 승격은 이번 범위에서 제외한다.
5. 에셋 프로젝트 원본을 개발 쪽에서 수정하지 않는다.

## 5. 규칙·스킬 병합
- 기획 스킬 `yal-game-planning`(v2: 자율 진행, Notion 자료 1순위, "혼자 못한다" 금지, 에셋은 GPT에게)을 **dev 공간 내장 스킬**로 이동하고 v3로 올린다. 개발 흐름을 `기획 → 설계 → 구현 → 검증`으로 정리하고 기획 산출물은 `docs/planning/`에 둔다. Notion 기준 스킬 `yal-game-design-criteria`도 dev로 이동한다.
- 마스터 MD(`src/main/master/MASTER.md`와 사용자 원본 동기화 경로): "기획 자율 진행"을 모든 개발 프로젝트에 적용하는 섹션으로 바꾸고, "기획과 개발의 경계" 섹션은 "에셋 프로젝트 참조 규칙"(§4)으로 대체한다. 스킬 도구 섹션의 `YAL_SPACE` 값 설명에 `assets`를 반영한다.
- 프로젝트에 IDE가 생성하는 CLAUDE.md/AGENTS.md 템플릿과 provisioner의 기본 문구를 새 구조에 맞게 갱신한다.
- **병합 마이그레이션**: 기존 `spaces/planning/skills`의 스킬을 `spaces/dev/skills`로 합친다. 이름이 같으면 dev 쪽을 유지한다. 사용자가 수정한 기획 스킬(내장본 해시와 다른 것)은 `<이름>-planning-legacy`로 별도 보존한다. 어떤 경우에도 덮어쓰지 않는다. 이동한 내용·충돌 결과는 로그로 남긴다.

## 6. 제거 대상 (동기화 장치)
- `src/main/planningSync.ts`, `planningSyncHandlers.ts`, `planningSyncIpc.ts`, `masterDoc.ts`의 planning 링크 동기화 부분, IPC 상수(`planningSyncStatus`, `planningApply`, `planningMarkSynced`, `planningSetBaseline`), 렌더러 `usePlanningSync.ts`, 변경 배지·「반영 완료」 계열 버튼, i18n 문구, `.claude/yal-planning-changes.md` 생성.
- 관련 테스트는 삭제하거나 새 구조에 맞게 바꾼다. 프로젝트 안에 이미 생성된 `.claude/yal-planning-changes.md` 같은 IDE 관리 파일은 다음 프로비저닝 때 IDE가 만든 것(마커 확인)만 정리한다.
- 에셋↔개발 링크의 선택 UI(드롭다운)는 유지하되 대상 종류를 `assets`로 바꾼다.

## 7. 비범위
에셋 자동 승격·동기화, 에셋 버전 관리 UI, 외부 에셋 스토어 연동, 여러 에셋 프로젝트 동시 연결.

## 8. 위험과 대응
- 레지스트리/스킬 폴더 마이그레이션 실패 → 이전 파일을 백업 폴더로 복사한 뒤 변환, 실패 시 원본 유지하고 알림.
- 대규모 제거로 인한 테스트 붕괴 → 제거와 신규 기능을 단계로 나눠 매 단계 테스트 통과 확인.
- 사용자 수정 스킬 손실 → §5의 보존 규칙과 마이그레이션 테스트.

## 9. 검증 기준
- `npm test`, `npm run typecheck`, `npm run build` 통과.
- 마이그레이션 테스트: planning→assets 레지스트리, 스킬 병합(충돌·수정본 보존), 링크 변환.
- 격리 앱 캡처: 탭 이름·목록 제목, 에셋 연결 드롭다운, 개발 프로젝트에 병합된 기획 스킬, 동기화 UI 제거, 기존 기획 프로젝트 자동 전환.
- 에셋 제작 가능 범위 테스트: GPT가 SVG·합성 SFX 샘플을 만들어 카탈로그에 기록하는 흐름을 1건 실행해 확인.
